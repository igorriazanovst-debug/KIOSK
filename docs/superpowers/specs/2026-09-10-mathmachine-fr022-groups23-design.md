## 0. Контекст и место в общем плане

Полный пересчёт по буквальному тексту ТЗ (`Тип6_трассировочная_матрица.md`, 2026-09-10) показал: FR-022 содержит **41 уникальную категорию** (не 13, не «~30» — обе прошлые оценки были неточными прочтениями строки 116 документа). На момент начала этого этапа реализовано 17 буквально + 6 через согласованное переосмысление = 23 из 41. Остаются **18 категорий**, ни одна не начата.

Пользователь: «я так понял, что группы 2 и 3 не сделаны, делаем, нужно соответствовать» — решение реализовать все 18 сразу, одним заходом, «обращая внимание на формулировки и другие аспекты, которые мы подмечали раньше» (грамматика/смысл/образовательная сторона, независимое ревью, value-bias/position-bias тесты вместе с генератором — уроки Эпика 12/30).

Также явно закрыт FR-009 (спец. инструмент ввода дроби): пользователь решил, что выбор большей дроби кнопками (`estimate_fraction`, Этап 3) — достаточная форма согласно самой формулировке ТЗ («…или выбрать целочисленный ответ из предложенных»), отдельный UI ввода числитель/знаменатель строить не нужно.

## 2. Класс А — детали генератора и визуалов

Продолжает паттерн `generateFR022Group1Content.ts` (Этап 3): `TopicSpec`/`GroupSpec`, `contentHash`+`rotate` для позиции/значения ответа, `buildGroup`/`mergeWaveIntoContent`. Новый файл: `packages/player/src/mathmachine/content/generateFR022Group2Content.ts`.

- **`count_then_add`/`count_then_subtract`**: визуал — два ряда точек/иконок (переиспользует `dotsRowStyle` из `TaskVisual.tsx`), текст задания формулирует обе операции в одном предложении («Посчитай кружки в первой группе, посчитай во второй, сложи вместе — сколько всего?»). Ответ — numeric (клавиатура), не choice, во избежание совпадения с value-bias риском на малом диапазоне сумм.
- **`clock_reading`**: визуал — SVG-циферблат (12 часов, часовая+минутная стрелка под конкретным углом, вычисляемым из `params.hours`/`params.minutes`). Ответ — choice из 3 вариантов времени (текстом «Ч:ММ»), только целые часы и половины на первую волну (упрощение по возрасту).
- **`mass_measurement`**: визуал — переиспользует силуэт весов из `WeightsTool` (статичная картинка, не интерактив) со стрелкой-указателем на конкретное деление шкалы; вопрос — «сколько показывают весы?», choice.
- **`right_angle_recognition`**: визуал — 3 угла разного размера (SVG `Line`/`path`, простые векторные лучи из общей вершины), один — ровно 90°; choice, какой из трёх прямой.
- **`shape_naming`/`shape_properties`**: визуал — простые SVG-фигуры (круг/квадрат/треугольник/прямоугольник/овал/пятиугольник — переиспользуется набор `SHAPE_POOL`-подобный принцип из `chainLogic.ts`, но новый, векторный, не эмодзи). `_properties` спрашивает про число сторон/углов — choice с числовыми вариантами.
- **`solid_naming`/`solid_properties`**: визуал — простые изометрические SVG-иконки 5 базовых тел (куб/шар/конус/цилиндр/пирамида) — минималистичная векторная графика в духе остального интерфейса (не 3D-рендер), с лёгкой псевдо-3D-штриховкой для читаемости на глаз ребёнка.
- **`spatial_position`/`spatial_direction`**: визуал — простая сцена (2-3 SVG-объекта на холсте с явным верх/низ/лево/право), вопрос про относительное положение или направление движения персонажа/стрелки; choice.
- **`spatial_ordering`**: визуал — 3 объекта разного размера/удалённости в ряд, choice какой из предложенных порядков (последовательностей подписей "А, Б, В") верный — тот же паттерн, что существующий `number_ordering`, но по зрительному, не числовому признаку.
- **`grid_coordinates`**: визуал — сетка 5×5 с подписанными осями (буква+число, школьный "шахматный" стиль), один объект помечен на пересечении; choice из 3 вариантов координат.

**Инвариантный тест-класс (обязателен, пишется ВМЕСТЕ с генератором, не постфактум — урок Эпика 12/30)**: для каждой choice-группы — `assertNoConstantAnswerPosition` (существующий) И `assertNoConstantAnswerValue` (введён в Этапе 3) там, где словарь вариантов ответа мал и переиспользуется между заданиями (часы, координаты, названия фигур/тел, направления) — это ПОЧТИ ВСЕ 13 новых групп, в отличие от Группы 1, где только 3 из 8 имели этот риск. Отдельно — тест на отсутствие тривиальной эвристики (например, для `right_angle_recognition`: прямой угол не должен всегда оказываться визуально самым большим/самым правым из трёх — рандомизировать позицию и относительный размер соседних углов).

**Независимое content-ревью** (отдельный агент, не автор генератора) — обязательно перед материализацией, по прямому прецеденту Этапа 3: формулировки, соответствие возрасту 4-9 лет, отсутствие путаницы терминов (например, чтобы вопрос про «прямой угол» не звучал как про «острый»/«тупой», которые в ТЗ вообще не требуются — не переусложнять).

## 3. Класс Б — общая архитектура 6 новых инструментов

Расширяет `packages/shared/src/mathmachine/model/schema.ts`:

```ts
export const MATH_TOOL_IDS = [
  'weights', 'chain', 'two_segments',
  'shape_construction', 'movement', 'deformation',
  'seriation', 'rotation_full_turn', 'symmetry',
] as const;
```

`LabScreen.tsx` — 9 кнопок вместо 3 (простое расширение существующего списка, без изменения самого компонента-меню).

Все 6 — **без авторского контента**, как и существующие 3 (параметризуемые на лету песочницы), react-konva, каждый со своей чистой логикой в `tools/<name>Logic.ts` (тестируется без DOM) + компонентом `tools/<Name>Tool.tsx` (drag/hit-testing, живая CDP-проверка обязательна — прецедент офсет/пивот-бага Весов в Этапе 1, который поймала только живая проверка, не юнит-тесты).

### 3.1 `shape_construction` (танграм-стиль)
- **Логика**: набор 2-4 готовых деталей (треугольники/квадраты фиксированных размеров, кратных базовой единице сетки) + целевой силуэт (квадрат/прямоугольник/более сложная фигура, чей контур точно собирается из этого набора — генерируется ОБРАТНЫМ способом: сначала берём готовый набор деталей в правильных положениях, ЗАТЕМ вычисляем их объединённый контур как целевой силуэт, чтобы гарантировать решаемость).
- **Взаимодействие**: перетаскивание (Konva `Draggable`) + поворот на 90° по клику/двойному клику на детали (полный произвольный угол поворота избыточен для этого возраста).
- **Проверка**: деталь считается «на месте», если её центр и угол поворота попадают в допуск (snap-радиус + кратность 90°) относительно предрасчитанной целевой позиции.

### 3.2 `movement` (маршрут по сетке)
- **Логика**: сетка N×N (5×5 или 6×6), стартовая клетка, целевая клетка, опционально 1 препятствие. Направление — 4 стрелки (вверх/вниз/влево/вправо) или прямой drag объекта по клеткам.
- **Проверка**: конечная позиция объекта совпадает с целевой клеткой, путь не проходит через клетку препятствия.

### 3.3 `deformation` (растянуть/сжать)
- **Логика**: исходная фигура (круг или квадрат) + целевая форма (эллипс с конкретным соотношением осей, или прямоугольник с конкретным соотношением сторон).
- **Взаимодействие**: перетаскивание маркера на стороне/углу фигуры меняет её пропорции в реальном времени (Konva `Transformer`-подобная логика, упрощённая — только 1-2 оси, не полный transformer с 8 хендлами).
- **Проверка**: итоговое соотношение сторон/осей попадает в допуск от целевого.

### 3.4 `seriation` (сериация по размеру)
- **Логика**: N (3-5) фигур одного типа, разного размера, в случайном начальном порядке + N пустых слотов в ряд, подписанных направлением (по возрастанию/по убыванию — случайно на задание).
- **Взаимодействие**: перетаскивание фигуры в слот (тот же hit-testing паттерн, что `ChainTool`).
- **Проверка**: порядок размеров в слотах строго монотонен в заданном направлении (не сверяется с ОДНИМ заранее вычисленным «правильным» порядком объектов, а проверяется свойство самой последовательности — устойчиво к тому, что несколько исходных объектов при равном размере переставимы, хотя генератор гарантирует уникальные размеры, чтобы избежать двусмысленности).

### 3.5 `rotation_full_turn` (полный оборот)
- **Логика**: фигура (например, стрелка или несимметричная геометрическая фигура — важно, чтобы 360° отличался от 0°/90°/180°/270° ВИЗУАЛЬНО, то есть сама фигура не должна быть поворотно-симметричной, иначе «полный оборот» неотличим от «оборот на 1/4» на глаз) в исходном положении.
- **Взаимодействие**: перетаскивание по дуге вокруг центра (Konva, угол вычисляется из позиции курсора относительно центра) вращает фигуру в реальном времени; live-накопление суммарного угла поворота (не просто текущий угол — важно, чтобы ребёнок должен был провернуть на 360°, а не просто держать курсор на исходном угле, иначе задание тривиально).
- **Проверка**: накопленный угол поворота ≥ 360° (с небольшим допуском) И финальный визуальный угол фигуры совпадает с исходным (0° по модулю 360°).

### 3.6 `symmetry` (дорисовать половину)
- **Логика**: ось симметрии (вертикальная, по центру холста), одна половина фигуры (простой силуэт — половина бабочки/домика/сердечка, набор 3-5 готовых силуэтов) готова, вторая — набор из нескольких «деталей-кандидатов» (часть из них — правильные зеркальные фрагменты, часть — дистракторы неправильной формы/положения).
- **Взаимодействие**: перетаскивание деталей-кандидатов на пустую половину.
- **Проверка**: каждая позиция на второй половине заполнена корректным (зеркально-верным) фрагментом.

### 3.7 Тестирование 3.1-3.6

Юнит-тесты чистой логики каждого инструмента (генерация всегда даёт решаемую конфигурацию — валидация «обратной генерацией» для конструирования, гарантированная уникальность размеров для сериации, гарантия визуальной асимметрии фигуры для вращения и т.д.), по прецеденту `weightsLogic.test.ts`/`chainLogic.test.ts`/`twoSegmentsLogic.test.ts`. Живая проверка drag/hit-testing на каждом — обязательна, не опциональна (прецедент офсет/пивот-бага Весов).

## 5. Последовательность реализации

1. Класс А (13 категорий) — низкий риск, известный паттерн: генератор+тесты вместе → независимое ревью → материализация в `pilotContent.json` → живая проверка → коммит. Аналогично Этапу 3.
2. Класс Б (6 инструментов) — по одному, в порядке возрастания сложности взаимодействия: `seriation` → `movement` → `rotation_full_turn` → `deformation` → `symmetry` → `shape_construction` (самый сложный — обратная генерация решаемого силуэта). Каждый — своя мини-спека логики (в этом документе, раздел 3), реализация, юнит-тесты, живая CDP-проверка drag-взаимодействия, коммит.
3. Обновление `Тип6_трассировочная_матрица.md` после каждого закрытого пункта (не пачкой в конце) — чтобы не повторить ошибку с «13 категорий», когда цифра расходится с кодом надолго незамеченной.
