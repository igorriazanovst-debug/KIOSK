## 1. Масштаб и фазировка

Требование ТЗ (FR-020/021) — ≥2800 заданий, ≥40 тем — на порядок больше любого предыдущего `ТипN`-проекта (для сравнения, Тип5 — 89 иллюстрированных объектов). Согласовано с пользователем: **два этапа**, как и в Тип5.

- **Этап 1 (этот план) — движок.** Полная механика: каталог, движок параметризуемых типов заданий, универсальный инструмент ввода ответа, один инструмент-лаборатория (Весы), звук/подсказки/прогресс — на небольшом пилотном наборе контента (2 темы, ~30–50 заданий).
- **Этап 2 (отдельный, позже) — контент.** Масштабирование до требуемых по ТЗ цифр: генерация экземпляров заданий по всем 40+ темам, оставшиеся 2 инструмента (Цепочка, Два отрезка), полная озвучка.

Этот документ и последующий план реализации — **только про Этап 1**. Этап 2 планируется отдельно, когда Этап 1 пройдёт живую проверку и появятся реальные цифры трудозатрат (решение пользователя: не оценивать общий бюджет токенов/времени заранее одним числом, а пересчитывать по факту после каждого этапа).

## 2. Архитектурное решение

Новый тип виджета KIOSK, рабочее имя **`mathmachine`** — по прямому решению пользователя: «это будет новый виджет с локальным хранением. это точно не тип 5 с сетевой трансляцией».

Обоснование: ТЗ, разд. 7 — «Настольное прикладное ПО с локальным хранением данных и встроенным модулем обновления, сохраняющее работоспособность без постоянного подключения к сети» — прямо исключает сетевую/многопользовательскую архитектуру Тип5.

- **Редактор** (`packages/editor-web`) — панель свойств виджета + отдельный редактор контента (дерево тем/групп/заданий), по образцу `NavigationPropertiesSection`/`NavigationEditorModal`.
- **Плеер** (`packages/player`, Electron) — автономный экран прохождения, читает контент из локального хранилища, работает офлайн.
- **Доступ на время разработки** — ограничен email `mokretcov.m@poznaikino.ru`, тем же двойным замком (сервер: 403 при сохранении/создании проекта с этим виджетом не тем email; клиент: пункт скрыт из `WidgetLibrary.tsx`), что уже есть у `chronolineAccess.ts`/`natcomAccess.ts` — новый файл `mathmachineAccess.ts` по их образцу.
- **Файловая структура** — по конвенции репозитория (маленькие дублируемые модули, не общий пакет): `editor-web/src/utils/mathmachine/{types,widgetType,catalog,taskEngine}.ts` и зеркально `player/src/mathmachine/{...}.ts`.

## 3. Модель данных

Версия схемы — с первого дня (иначе первую же миграцию будет некуда вставить).

```
MathMachineData (version: "1.0")
├── catalog: Section[]                    // разделы верхнего уровня
│   └── subsections: Subsection[]
│       └── topics: Topic[]               // листовая тема
│           └── groups: Group[]           // группа заданий по теме
│               └── taskIds: string[]     // первый = обучающее задание группы
├── tasks: Record<taskId, Task>
│   {
│     id, typeId,                          // ссылка на зарегистрированный тип
│     params: Record<string, unknown>,     // параметры конкретного экземпляра
│     hintRef?: string,                    // подсказка (по умолчанию — общая для typeId)
│     audioTaskTextId?: string,            // озвучка текста задания (см. разд. 6)
│   }
├── mathTools: MathTool[]                  // Весы (Этап 1); Цепочка/Два отрезка — Этап 2
└── media: Record<mediaId, MediaAsset>     // картинки/аудио, стабильные ссылки по id
```

Отдельно, **вне** пакета контента — пользовательские данные (не трогаются обновлением контента):

```
UserData (в пользовательском каталоге устройства, не в установочном пакете)
├── progress: Record<groupId, {done: taskId[], current: taskId}>
├── settings: { soundOn: boolean }
└── favorites?: taskId[]                   // если решим делать (см. разд. 5)
```

## 4. Движок параметризуемых типов заданий

Ядро масштабируемости к Этапу 2. Тип задания — это код (не данные): id, схема параметров, React-компонент отрисовки, функция проверки ответа, ссылка на подсказку/обучающую демонстрацию. Экземпляр задания — просто `{id, typeId, params}`.

Пилотные типы (Этап 1, 5–6 штук):

| typeId | Тема | Что делает | Режим ответа |
|---|---|---|---|
| `number_counting` | Счёт | посчитать объекты на картинке | клавиатура/лента цифр |
| `number_sum_two` | Сложение | сложить два числа | клавиатура/лента цифр |
| `number_sum_three` | Сложение | сложить три числа | клавиатура/лента цифр |
| `number_missing` | Счёт | вставить пропущенное число в ряд | клавиатура/лента цифр |
| `compare_length` | Сложение\* | выбрать больший/меньший из двух | выбор из активных элементов |
| `fraction_part_of_the_whole` (опционально, если позволит время) | — | выбрать долю целого | инструмент ввода дробей |

\* `compare_length` добавлен ради проверки режима «выбор», не привязан жёстко к теме «Сложение» — можно вынести в третью мини-тему при реализации, если так чище.

Каждый тип задания **один раз** определяет свою обучающую демонстрацию (переиспользуется во всех своих экземплярах — так подсказка при первой ошибке остаётся дешёвой по контенту).

Пайплайн Этапа 2 (не реализуется сейчас, но модель данных должна его не блокировать): скрипт генерирует N экземпляров типа с непересекающимися параметрами на тему/группу, пока не наберётся нужное число уникальных заданий.

## 5. Каталог и навигация

```
Раздел → Подраздел → Тема (лист, содержит группы) → Группа заданий (начинается с обучающего задания)
```

UI: рубрикатор (разделы→подразделы→темы) + статус-бар группы (текущее/пройдено/не пройдено, светло-зелёный/тёмно-зелёный/прозрачный — как у оригинала).

**Не входит в Этап 1** (есть у оригинала, но ТЗ этого не требует явно — FR-018 требует только структурированный каталог): поиск по ключевому слову, «Избранное», «Случайные задания». Оставлены как возможная полировка позже, чтобы не путать неформальный ориентир «как у оригинала» с обязательным FR (тот же урок, что уже был зафиксирован в Тип5 по числу объектов).

## 6. Проверка ответа, подсказки, озвучка

Состояние попытки на одно задание:

1. Ввод/выбор ответа → «Ответить».
2. **Верно** (FR-012) → позитивная анимация → авто-переход к следующему заданию, сегмент прогресс-бара — «пройден».
3. **Неверно, попытка 1** (FR-010) → автоматически проигрывается обучающая демонстрация типа задания → повторный ввод разрешён.
4. **Неверно, попытка 2 подряд** (FR-011) → показывается правильный ответ → переход дальше.

Управление заданием: «Начать сначала» (FR-015, сбрасывает попытки ТЕКУЩЕГО задания, не всей группы) · «Закрыть» (FR-017, выход из группы в каталог) · переключатель звука (FR-016, глушит озвучку/подсказки, не блокирует ответы).

Обучающая часть группы (FR-005/127) — первое задание группы, отдельный вид: демонстрирует механику и объясняет правило, тоже озвучено.

**Озвучка — офлайн, без живого TTS в рантайме.** Продукт обязан работать без сети (ТЗ разд. 7, FR-025). Все аудиофайлы (текст задания, обучающие части) генерируются **на этапе создания контента** через TTS-сервис и зашиваются в дистрибутив как обычные медиафайлы — ровно как оригинал шьёт 2834 готовых MP3, никакого сетевого вызова во время игры. Одна озвучка на экземпляр задания (не склейка фраз из кусочков — надёжнее).

## 8. Контент: стиль и легальность

Оригинал — чужой охраняемый контент (картинки, звук), использовать нельзя (ТЗ прямо требует легальность материалов). Решение пользователя: **свой визуальный стиль через syntx.ai** (как в Тип5, где по этой же причине весь арт перерисован заново) **+ голос через TTS-сервис** для текстов заданий (не чужие файлы). Художественный стиль/маскот — решить перед началом генерации контента Этапа 1 (отдельный маленький вопрос, не блокирует эту спеку).

## 9. Отказоустойчивость и нефункциональные требования (ТЗ разд. 9)

- Битый/неполный JSON контента — не приводит к падению приложения, проблемный узел пропускается с предупреждением в лог (не тихо, не молча).
- Сохранение прогресса — атомарно (запись во временный файл + переименование), не должно портиться при обрыве.
- Удаление медиафайла — проверяет отсутствие ссылающихся живых заданий (ТЗ разд. 7 требует контроль связанных объектов).
- Обновление контента не должно стирать `UserData` (прогресс/настройки) — данные физически разделены (разд. 3).
- **Планшеты (FR-004):** по решению пользователя — Windows-планшеты через тот же Electron-плеер с сенсорным UI, без отдельной сборки. **Android-версия — в бэклог будущих плановых обновлений**, не в этот план (прямое решение пользователя: «сохрани в список задач для будущих плановых изменений»).
