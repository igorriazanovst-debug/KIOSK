## 1. Источники и ограничение точности

Функциональные требования — из `ТЗ_07_Рус_IQ.docx` напрямую (unzip +
`word/document.xml`, узлы `w:t`), не по пересказу — урок ретроспективы
Тип6 (там оценка объёма ТЗ трижды расходилась именно из-за цитирования
вместо сверки с оригиналом). Устройство оригинала — по разбору дампа
`app_dump`/`app_src` (Electron 8 + Vue 2, восстановлено из карт кода) и
живому прогону Плеера, см. `РусIQ_3.1.1_разбор.md`, раздел 4.

**Явно принятые решения, отклоняющиеся от буквального прочтения ТЗ** (см.
диалог брейнсторминга 2026-09-10):

1. **FR-018** («экспорт в отдельный файл… без установки продукта») —
   реализуется как экспорт/импорт файла викторины МЕЖДУ проектами KIOSK,
   открываемый уже установленным лицензированным Плеером — не отдельный
   автономный исполняемый файл. У KIOSK нет прецедента непривязанного к
   лицензии исполняемого артефакта; создание второго сборочного пайплайна
   вне обычной модели лицензирования признано неоправданным расширением
   объёма для этой фазы.
2. **FR-009** (соревнование 2-3 участников) — одно устройство, поочерёдные
   ходы (как в оригинале и как настольная игра), НЕ сетевое подключение с
   разных устройств. Явно исключено по решению пользователя, чтобы не
   повторить архитектурную сложность Тип5 (там межустройственность
   потребовала встроенный Express+socket.io сервер — здесь он не нужен).
3. **Контент** — переиспользуется структура/тексты/координаты из
   `app_dump/extra/default.oc3rusiq` (встроенная методическая викторина
   оригинала, 458 вопросов/13 тем) как база, поверх которой добавляется
   собственный контент до ≥600 вопросов/≥15 тем (запас над порогом
   ТЗ ≥450/≥12, по аналогии с «Матемашкой», решение пользователя).
   **Открытый юридический риск, принят пользователем осознанно**: прямое
   переиспользование текстов вопросов конкурентного коммерческого продукта
   не проверялось на чистоту как компиляция — если продукт пойдёт в
   реальную поставку заказчику, рекомендуется юридическая проверка перед
   этим шагом (не блокирует разработку и тестирование).

## 2. Границы Фазы 1

**Входит:**
- Виджет `rusiq` — standalone-app полноэкранное Electron-приложение внутри
  KIOSK Player.
- Формат данных викторины (версионированная схема), формат перечня
  пользовательских результатов.
- Полный игровой поток: интро → число игроков → имена → уровень сложности →
  число вопросов на игрока (FR-019) → игровое поле → результаты (сводка +
  детализация).
- Механика: точки-ответы на изображении, таймер с убыванием баллов,
  пропуск вопроса, поочерёдные ходы, уникальные вопросы по уровню.
- Один встроенный набор контента (см. раздел 8), парольная защита викторины
  от изменений на уровне формата данных (сам механизм проверки пароля — UI
  ввода пароля нужен только когда появится Редактор в Фазе 2; в Фазе 1
  поле присутствует в схеме, но не редактируется через UI).
- Allow-list доступа к редактированию ПРОЕКТА с этим виджетом
  (`mokretcov.m@poznaikino.ru`, тот же паттерн что Хронолайнер/Матемашка).
- Локальное хранение пользовательских данных (история результатов) через
  IPC-мост.
- Экспорт/импорт файла викторины между проектами (раздел 4).

**НЕ входит (Фаза 2 или позже):**
- Визуальный Редактор викторин (создание/правка вопросов, расстановка точек,
  загрузка пользовательских изображений, спецсимволы, UI ввода/проверки
  пароля).
- Печать результатов и отправка по e-mail (`MailSender.exe` в оригинале) —
  явно не упомянуто пользователем как приоритет; включить в объём Фазы 2 или
  отдельным маленьким треком после Фазы 1, если понадобится для приёмки
  FR-010/011 в буквальном прочтении (сводка/детализация на экране уже
  закрывают основной смысл требования).
- Автообновление (FR-025) — уровень платформы KIOSK, не виджета (тот же
  вывод, что и в трассировке Тип5/Тип6 для сравнимых платформенных пунктов).
- Визуальная идентичность/маскот — по прецеденту Матемашки, отдельный шаг
  после функциональной полноты, не блокирует Фазу 1.

## 4. Формат данных викторины

Один JSON-файл (не ZIP-контейнер, как в оригинале — не нужен, поскольку нет
цели создать читаемый сторонним ПО архив; изображения хранятся рядом как
отдельные файлы с устойчивыми ссылками по имени, требование ТЗ раздел 7).

```ts
interface RusiqQuiz {
  schemaVersion: 1;                 // с первого дня — урок playbook §2
  id: string;
  title: string;
  intro: string;                    // текст интро-экрана
  themes: string[];                 // список тем (для интро-экрана)
  passwordHash: string | null;      // парольная защита (FR-016); null = без пароля
  image: { fileName: string; width: number; height: number };
  levels: { id: 1 | 2 | 3; label: string }[];  // «Начинающий/Опытный/Профессионал»
  questions: RusiqQuestion[];
  fakePoints: { x: number; y: number }[]; // общие ложные точки поля
}

interface RusiqQuestion {
  id: string;
  text: string;
  answer: string;
  helpText: string;                 // подсказка, может быть пустой строкой
  x: number;
  y: number;
  price: number;                    // вес в баллах, максимум за мгновенный верный ответ
  timeSeconds: number;
  level: 1 | 2 | 3;
  theme: string;
}
```

**Экспорт/импорт между проектами (реализация FR-018 по решению раздела 1
п.1):** сериализация `RusiqQuiz` + копирование файлов изображений в новый
проект, десериализация с валидацией схемой (`safeParse`, тот же принцип, что
`MathMachineUserDataSchema` — недоверенные данные с границы всегда через
одну функцию валидации, не через голый `JSON.parse`).

## 5. Модель вопроса — механика

- Каждый вопрос привязан к точке `(x, y)` на общем тематическом изображении.
- Игрок кликает по точке в отведённое время (`timeSeconds`).
- Балл начисляется пропорционально остатку времени на таймере (быстрый
  верный ответ → ближе к `price`, медленный → меньше; 0 при неверном
  ответе или истечении времени) — та же механика, что в оригинале
  (раздел 5 СПЕЦИФИКАЦИИ воспроизведения).
- Ложные точки (`fakePoints`) отображаются наравне с настоящими — клик мимо
  правильной точки не засчитывается.
- **Новый класс защиты от предсказуемости** (аналог урока playbook §12 про
  контент-генераторы, но здесь ось другая — не позиция кнопки, а
  геометрия): тест-инвариант на этапе материализации контента должен
  проверять, что правильные точки не кластеризуются в предсказуемый регион
  изображения (например, всегда в одной четверти) и что распределение
  ложных точек относительно правильных не даёт эвристики «выбери
  ближайшую/самую заметную точку» без чтения вопроса.

## 6. Экраны и поток игры

```
Интро (описание + список тем, кнопка «Играть»)
   ↓
Число игроков (1 / 2 / 3)
   ↓
Имена игроков
   ↓
Уровень сложности (Начинающий / Опытный / Профессионал)
   ↓
Число вопросов на игрока (FR-019 — выбор из нескольких готовых
                          значений, не произвольный ввод)
   ↓
Игровое поле (тематическое изображение + точки, инфопанель:
              вопрос N/M, таймер, убывающие очки, имя текущего игрока,
              кнопка «Сдаюсь» — пропуск хода)
   ↓
Результаты (сводка по игрокам: баллы, верных ответов, время;
            кнопка «Подробнее» → детализация по каждому вопросу)
```

Общая обвязка экранов (шапка/кнопки действий/баннер) — переиспользовать
`ToolShell.tsx`/`ToolFeedbackBanner.tsx` из `packages/player/src/mathmachine/tools/`
если стилистически подходят, либо завести аналогичную пару компонентов в
`packages/player/src/rusiq/` — решить при реализации по факту, насколько
переиспользование уместно вне каталога `mathmachine`.

- **Чистая логика без DOM** (`packages/player/src/rusiq/*.test.ts`):
  подсчёт баллов по остатку времени, очерёдность ходов, назначение

  временный `window.__rusiqDebug` хук (playbook §5, находка сегодняшней

- Приёмочная сверка Фазы 1 — построчно против FR из таблицы раздела 0,
  помеченных «1» (полностью в этой фазе) или «1 —» (частично, с явным
